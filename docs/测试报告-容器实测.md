## 4. bug 清单

### BUG-1（阻断）PHP 7.4/8.0 无法编译：`mre_mysql.c:201` 使用 `bool` 未加版本守卫

- 位置：`mre_mysql.c:199-210`，`mre_hook_fetch_row()` 的**函数定义**无
  `#if PHP_VERSION_ID >= 80100` 守卫（其前向声明 L223-225 与赋值点 L232-236 均有守卫），
  参数 `bool *fetched_anything` 在 7.4/8.0 头文件下是未知类型（8.1+ Zend 才有 `bool`）。
- 现象：`phpize && ./configure --enable-mre && make` →
  `/tmp/mre-test/src/mre_mysql.c:201:44: error: unknown type name 'bool'`，`make` Error 1。
  另有 `mre_config.c:56`/`mre_script.c` 的 INI_STR const 丢弃限定符警告（非致命）。
- 最小复现：7.4 容器内 `phpize && ./configure --enable-mre && make`（`tests/docker/README.md`）。
- 影响：7.4/8.0 完全无法出包；README 声称兼容 7.4 与 8.0~8.4，实际 7.4/8.0 编译失败。
- 佐证：8.4 原样 make_exit=0。
- 临时绕过（测试用，未改源码）：`make CFLAGS="$CF -include stdbool.h"`。

### BUG-2（严重）PHP 7.4 log_script 抛异常 → 进程 SIGSEGV

- 现象：`MRE_LOG_SCRIPT` 脚本对某条记录 `throw new RuntimeException(...)` 时，7.4 进程
  **段错误退出（exit 139）**；该记录与其后的所有日志丢失，无 `type:"warn"` 降级告警。
  8.4 同场景 exit=0：记录降级写主日志、一次性 `type:warn` 告警，后续请求不受影响
  （与 README 声明的降级语义一致）。
- 最小复现：`tests/docker/scripts/t12_crashrepro.php` + `cb_t12.php`
  （`run-matrix.sh repro`）。
  ```sh
  docker exec -e MRE_ENABLE=1 -e MRE_LOG_FILE=/tmp/mre-test/logs/t12.json \
    -e MRE_LOG_SCRIPT=/tmp/mre-test/scripts/cb_t12.php 7.4-alpine-php-dev \
    php -d extension=/tmp/mre-test/src/modules/mre.so /tmp/mre-test/scripts/t12_crashrepro.php
  # 输出停在 "before-boom"，exit=139；8.4 容器同命令 exit=0 全部输出
  ```
- 定位方向：`mre_script.c` 异常捕获/`zend_clear_exception` 恢复路径在 7.4 的 API 差异
  （7.4 进程内实测必现，确定性 3/3）。

### BUG-3（严重）PHP 7.4 全部 ini 配置静默失效：`INI_STR` 传 `const char*` 变量被 `sizeof(name)-1` 截断为 7 字节查找

- 位置：`mre_config.c:54-61` `mre_ini_str()` 将 `const char *name` 形参传给宏
  `INI_STR(name)`；7.4 的宏为 `#define INI_STR(name) zend_ini_string_ex((name), sizeof(name)-1, 0, NULL)`
  —— 对指针求 `sizeof` 得到 **7**，即所有 ini 名按前 7 字节匹配。
- 后果（7.4 实测）：
  - `mre.gtx_timeout`（15 字符）截断为 `mre.gtx` → 命中已有条目 `mre.gtx`（值 "0"）→
    atoi=0 → 钳到下限 10。实测：`ini_get("mre.gtx_timeout")="300"` 但
    `mre_gtx_status()["timeout"]=10`；`-d mre.gtx_timeout=777` 也得 10；仅
    `MRE_GTX_TIMEOUT` 环境变量生效（env 路径正常，=500 → 500）。
  - `mre.enable/mre.log_file/mre.log_format/mre.sample_rows/mre.state_dir/mre.yaml_config/
    mre.log_script/mre.capture_*` 截断后均无 7 字节同名条目 → 查找失败 → 全部退回代码内
    fallback。**纯 ini 部署实测完全无效**：`php -d extension=mre.so -d mre.enable=1
    -d mre.log_file=/tmp/mre-test/logs/ini-only.json ...` 后日志文件未创建
    （7.4 ABSENT；8.4 同命令 PRESENT）。
- 8.4 不受影响：8.x 的 `INI_STR` 宏基于 `strlen(name)`，实测 no-env=300、env=500、
  ini=777 全部正确。
- 最小复现：`tests/docker/README.md`「bug4 repro」段 + 上面的 ini-only 命令。
- 影响：7.4 上 php.ini/fpm 部署形态（不走环境变量）整条配置链路失效，包括总开关。

### 观察项（非 bug，记录口径）

- O1 `mysqli_stmt` 的 `bind_result()+fetch()` 取行路径不产生行采样（`stmtgetresult` 路径正常，
  `tests/docker/run-matrix.sh probe` 可复现：stmtbind fetched_lines=0）。
  README「行内容采样：mysqli 全覆盖」的口径偏乐观，实际覆盖 fetch_into/fetch_row 实例钩子
  可达的路径。
- O2 PDO 行采样在 7.4 无、8.4 有——设计文档已声明的版本限制，实测与文档一致。
- O3 yaml/脚本路由按单条记录的 `content` 匹配：SELECT 的 req 行落规则文件，其 resp
  （content=`result`/采样行）不匹配规则落 default——设计即"按内容路由"，测试按此断言。
- O4 S7 中窗主 A 的 `final-state` 可观察到 `mark_rollback`（A 的轮询先于 B 收尾完成），
  最终注册表正确删除、状态 `none`，数据面正确；属测试等待条件写法而非扩展缺陷。

## 5. 结论

**达到"日志能真实记录"的目标**：在真实容器 + 真实 mysql8/redis 上，
- `MRE_*` 环境变量配置路径下，S1~S9 全部通过：mysqli/PDO 收发（SQL 文本、影响行数、
  错误码/sqlstate、行采样）、redis RESP 双向（phpredis 与裸 stream/Predis 路径）、
  json/text 双格式、`/proc/1/fd/1` 直达 docker logs、yaml 规则路由、脚本回调路由、
  跨进程全局事务回滚/提交，全部真实落盘且 json-lines 合法、无空行半行、无多余段错误
  （除 BUG-2 场景）。
- 8.4 容器原样编译 + S1/S4/S5 复跑全绿，8.x 兼容性得到实证；PDO 8.1+ 行采样实测生效。

已验证的配置组合：`MRE_ENABLE`/`MRE_LOG_FILE`（普通文件、/proc/1/fd/1）/`MRE_LOG_FORMAT`（json、text）/
`MRE_SAMPLE_ROWS`（0/1/2/3/5）/`MRE_CAPTURE_REDIS=0`/`MRE_YAML_CONFIG`（2 规则+default）/`MRE_LOG_SCRIPT`
（headers/post/uri/null/异常）/`MRE_GTX=1`+`MRE_STATE_DIR`（跨进程 rollback/commit）；ini 配置路径仅在
8.4 验证通过（7.4 因 BUG-3 失效）。

**但不得视为可直接发布**：7.4（用户指定参考版本）存在 BUG-1（无法编译）、BUG-2（脚本异常
段错误）、BUG-3（ini 配置全失效）三个必须修复的问题；修复前 7.4 生产部署（尤其 fpm/php.ini
形态）不可用。
