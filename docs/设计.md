# mre（mysql-redis-extend）架构设计

> 阶段A：扩展核心（env 配置、mysqlnd 捕获、redis 嗅探、日志写入、GA 编译）。
> 阶段B：yaml 规则引擎（PCRE2）、脚本回调日志路径、跨 fpm 全局事务。
> 本文记录实现原理与关键取舍；用户视角的配置/函数说明见 `README.md`。

## 1. 总体架构

```
用户态                       扩展内部                        输出
──────                      ────────                       ─────
mysqli / PDO_MYSQL ──► mysqlnd ──► [mre_mysql.c 方法表挂钩] ─┐
phpredis / Predis  ──► PHP streams ──► [mre_redis.c ops 包装] ─┤─► [路由: 脚本>规则>主日志] ─► [mre_log.c] ─► 文件/stdout/stderr//proc/1/fd/1
                                                            │        ▲           ▲
php.ini + 环境变量 ──► [mre_config.c env>ini 解析] ──────────┘        │           │
yaml 规则文件 ──► [mre_yaml.c 解析器] ──► [mre_rules.c PCRE2 规则] ───┘           │
mre.log_script ──► [mre_script.c 脚本回调（每记录执行）] ─────────────────────────┤
mre_gtx_* / mysqlnd 钩子 ──► [mre_gtx.c 注册表+flock] ─(收尾 ROLLBACK/COMMIT)─► [mre_mysql.c]
```

生命周期：

- **MINIT**：注册 INI → 解析一次配置 → 安装 redis 工厂钩子与 mysqlnd 方法表钩子 → 加载 yaml（规则随之编译）。
- **RINIT**：重新解析配置（env 可能变）→ yaml 变更检测/热加载（规则重编译）→ 脚本回调可用标志复位、gtx 检查纪元递增 → 钩子自愈（reassert / rehook）。
- **RSHUTDOWN**：禁用脚本回调（executor 关闭后不可再执行用户代码）。
- **MSHUTDOWN**：还原工厂与方法表 → 释放规则缓存与 yaml 树 → 关闭日志句柄 → 注销 INI。

## 2. MySQL 捕获：mysqlnd conn_data + stmt 方法表覆盖

### 2.1 为什么选方法表覆盖

候选方案对比：

| 方案 | 结论 |
|---|---|
| mysqlnd conn_data 方法表覆盖（`mysqlnd_conn_data_set_methods` / `mysqlnd_stmt_set_methods`） | **采用**。这是 mysqlnd 官方暴露的插件级扩展点（`mysqlnd_ext_plugin.h`），位于 mysqli/PDO 之下，天然覆盖所有连接类；不需要改 PHP 核心。 |
| 官方 observer API | php-src 从未合并过正式的 query observer（历史上仅停留在 RFC/补丁），各版本无稳定 API，不可依赖。 |
| 钩 mysqli/pdo 函数表（`zend_function` 替换） | 太上层：每个用户类/对象 handlers 都要覆盖，且抓不到协议层信息（受影响行数、sqlstate），放弃。 |

### 2.2 实现要点

- **挂钩点**：`conn_data.query / store_result / use_result / next_result / dtor`，`stmt.prepare / stmt.execute / stmt.get_result`，结果对象实例级 `res->m.fetch_into`（全版本）与 `res->m.fetch_row`（仅 8.1+，见 §4）。
- **委托**：MINIT 时把当前（可能已被其他插件链接过的）方法表**整表拷贝**，保存被覆盖条目的原指针，调用前转发。方法表是 mysqlnd 在建连时通过 `data->m = mysqlnd_conn_data_get_methods()` 赋给每个连接的共享指针，因此 MINIT 里 set_methods 之后建立的所有连接都走我们的表；`RINIT` 每请求用一次指针比较自愈（防其他扩展后注册覆盖）。
- **每连接上下文**：通过官方插件机制 `mysqlnd_plugin_register()` 拿到 plugin_id，用 `mysqlnd_plugin_get_plugin_connection_data_data(conn, id)` 获得挂在连接对象尾部的槽位（连接分配时已按 plugin_count 预留，`pecalloc` 清零），存放"最近 SQL、采样预算、行数"等状态，随连接释放（`dtor` 钩子里 `pefree`，持久标志跟随 `conn->persistent`），无泄漏、无线程问题。
- **数据取用**：
  - SQL：`query(conn, query, len)` / `stmt_prepare(stmt, query, len)` 入参原文；
  - 影响行数：`conn->upsert_status->affected_rows`（`(uint64)-1` 表示"不适用"，如 SELECT 之后，日志中省略）；
  - 错误：`conn->error_info` / `stmt->data->error_info` 的 `error_no / error / sqlstate`；
  - 结果元信息：`res->field_count`、`res->m.num_rows(res)`（缓冲结果），非缓冲置 `truncated`；
  - 行采样：包装 `res->m.fetch_into`（mysqli 全部取行路径、PDO 8.1+ 的 `fetch_row` 也走它）与 `res->m.fetch_row`（8.1+，覆盖 PDO 的 `mysqlnd_fetch_row_zval`）。`bind_result()+fetch()` 取行路径在各版本都走 **stmt 方法表 `fetch`**（7.4/8.0 传 stmt 指针、8.1+ 也不携带行数组），因此另挂 `stmt.fetch` 钩子，读取绑定变量 `stmt->data->result_bind[i].zv`（去引用）拷成临时行数组后复用同一采样器；该路径采样行不带 `rows` 总数元信息。采样只读行数组的前 N 行（`mre.sample_rows`），格式化为 `a|b|c` 摘要，不动结果游标、不影响业务取行。

### 2.3 已知限制

- PDO 在 7.4/8.0 的缓冲结果行抓取走 C 数组路径（`m.fetch_row` 的 `void*` 参数在 7.4/8.0 存在 stmt 绑定取行复用同一槽位的类型歧义，为安全起见不包装），因此 7.4/8.0 上 PDO 只记元信息不采样行内容；8.1+ 起所有 `m.fetch_row` 调用点均为 `zval**`，安全覆盖。
- mysqli `bind_result()+fetch()` 的采样经 stmt `fetch` 钩子实现，行内容取自绑定变量，采样行不含 `rows` 总数元信息（`get_result` 路径含）。
- 异步 API（`send_query/reap_query` 直用）、`multi_query` 的首个结果之外的 use/store 已覆盖，`more_results` 布尔查询不单独记日志。
- mysqlnd 以独立 `mysqlnd.so` 分发的发行版（Debian/Ubuntu 包）必须先加载 mysqlnd 再加载 mre（README 已写明），因为插件区 getter 是数据符号，dlopen 时即需解析。

## 3. Redis 捕获：streams 传输层嗅探

### 3.1 为什么在 streams 层做

要求"不管哪种类都支持"。phpredis（`Redis`/`RedisCluster`）是 C 扩展，其 socket 通过 `php_stream_xport_create()` 创建；Predis 是用户态类，走 `fsockopen`/`stream_socket_client`，最终同样进入 `php_stream_xport_create()`。两者在 PHP 内的唯一公共汇合点就是 **streams 传输层**：

```
phpredis ──────────────┐
                       ├──► php_stream_xport_create("tcp://host:port") ──► xport_hash["tcp"] 工厂
fsockopen/stream_socket_client ─┘
```

因此覆盖了传输层就覆盖了所有"连接类"。`tls://`、`ssl://`、`unix://` 是独立协议名，不属于本阶段嗅探范围。

### 3.2 实现要点

- **工厂包装**：MINIT 用 `php_stream_xport_get_hash()` 取出当前 `"tcp"` 工厂（可能是内置的 `php_stream_generic_socket_factory`，也可能是 openssl 注册的 ssl 感知工厂）保存为原工厂，再 `php_stream_xport_register("tcp", mre_tcp_factory)`。我们的工厂**始终原样委托**原工厂建连（保留 bindto 等流上下文与 openssl 行为），仅当协议为 `tcp` 且 `resourcename` 解析出的端口等于 `mre.redis_port` 时，对该返回的 stream 做包装。`RINIT` 每请求检查 hash 内指针是否仍是我们，若被后加载的扩展（如 openssl）覆盖则重新注册（自愈）。
- **ops 包装**：把 `stream->ops`（`php_stream_socket_ops` 等）整结构拷贝到一块**随 stream 持久性一致分配**的内存（`pemalloc(size, stream->is_persistent)`），改写 `write/read/close` 三个入口，`stream->ops` 指向拷贝。持久化连接（pconnect / persistent id）在复用时不经过工厂，包装随流存活、语义正确。`close` 包装先调用原 close、**恢复 `stream->ops` 原指针后再释放包装内存**（引擎在 close 返回后仍可能读 `stream->ops`，否则构成 use-after-free——开发期实测踩过并已修复）。
- **RESP 双向增量解析**（纯状态机，可处理任意分包/粘包）：
  - 请求方向（write）：`*N` → 逐个 `$len` 参数，参数按字节计数精确消费（二进制安全），拼成 `CMD arg1 arg2 ...` 摘要；首字节非 `*` 的旧式 inline 命令按行记录。
  - 响应方向（read）：`+ - :` 行回复、`$len` bulk（内容截断摘要）、`$-1` null、`*N` 数组（记 `*N` 条数摘要，用深度栈处理嵌套数组）。每个顶层回复一条日志。
  - 全部为有界缓冲 + 截断标记，嗅探是旁路行为：解析异常只影响日志完整性，不影响连接与业务数据。
- **发送顺序语义**：write 包装在原 write 成功后记录（记录"实际发出的字节"），read 包装在原 read 成功后记录。

### 3.3 局限（与 README 一致）

- 不覆盖 `tls://` / `ssl://` 的 redis（它们注册的是 openssl 工厂、协议名不同）与 unix socket redis。
- phpredis 的 `pconnect` 持久连接在**首次**建连时被包装并随流存活，行为正确；但嗅探开关/端口配置在连接建立后改变，不影响已存在的持久流。
- 数组回复不展开元素内容（只记条数），业务上等价信息可用 bulk 摘要覆盖大多数命令（GET/SET/HGETALL 的元素等为 bulk）。
- 客户端若使用 pipeline，多条命令仍逐条解析记录（按 RESP 边界），回复按回复边界逐条记录。

## 4. 版本兼容策略（7.4 / 8.0 ~ 8.4）

所有差异集中在少量 `PHP_VERSION_ID` 分支，且**每个分支点都对照 php-src 各分支源码逐一核实过**（7.4 / 8.0 / 8.1 / 8.2 / 8.4）：

| 差异点 | 版本边界 | 处理 |
|---|---|---|
| `conn_data::store_result / use_result` 的 `flags` 参数 | 8.0 有、8.1 起移除 | `#if PHP_VERSION_ID < 80100` 双签名 |
| `res::fetch_into` 的 `enum_mysqlnd_extension ext` 尾参 | 同上 | 同上（含 `ZEND_FILE_LINE_DC` 宏，debug/非 debug 均匹配 typedef） |
| `res::fetch_row` 参数类型 `void*` → `zval**`（伴随 Zend 引入 `bool` 类型） | 8.1 起 | `mre_hook_fetch_row` 的**定义、前向声明、赋值点**三处用同一 `#if PHP_VERSION_ID >= 80100` 守卫（容器实测 BUG-1：定义处漏守卫导致 7.4/8.0 `make` 报 `unknown type name 'bool'`）；7.4/8.0 的 stmt 绑定取行改由 stmt `fetch` 钩子采样 |
| `INI_STR()` 宏对指针参数做 `sizeof(name)-1` | 7.x（8.0 起改 `strlen`） | 不使用该宏：`mre_ini_str()` 按真实长度直接调 `zend_ini_string_ex()`（容器实测 BUG-3：`mre.gtx_timeout` 被截断为 `mre.gtx`，7.4 全部 ini 配置静默失效）；7.x 原型带非 const `char*` 形参，调用点显式转换 |
| `zend_register_ini_entries` 返回值/签名演变（8.2 起 `zend_result`，`_ex` 带 module type） | 8.2 起 | 统一使用 `REGISTER_INI_ENTRIES()` / `UNREGISTER_INI_ENTRIES()` 宏，跨版本安全 |
| INI 定义宏（`PHP_INI_ENTRY`，位于 `main/php_ini.h`） | 无差异 | 直接使用 |
| 模块全局宏（`ZEND_DECLARE_MODULE_GLOBALS` 等）、`ZEND_MODULE_GLOBALS_ACCESSOR` | 无差异 | 用引擎宏，ZTS/非 ZTS 自动正确 |
| `php_stream_transport_factory` typedef、`php_stream_xport_get_hash`、`php_stream_generic_socket_factory` 导出 | 无差异（已核对 7.4 与 8.4 头文件 diff） | 直接使用 |
| `mysqlnd_plugin_register(void)` / xetters / plugin area | 无差异（7.4/8.2/8.4 一致） | 直接使用 |
| `config.h` 引入位置 | — | 统一在 `php_mre.h` 顶部 `#ifdef HAVE_CONFIG_H` 引入，保证各编译单元的 `HAVE_MRE_MYSQLND` 一致（否则出现符号缺失） |

线程安全：全部共享状态使用模块全局（`MRE_G`，ZTS 下为线程本地）；跨请求生命周期内存一律 `pemalloc/pestrdup(…, 1)`（日志句柄路径缓存、yaml 树、redis ops 包装、mysql 连接上下文），请求级内存一律 `emalloc` 家族，避免请求结束时被 MM 回收后再次释放（开发期实测修复：`estrdup` 缓存日志路径导致退出时 double free）。

## 5. 日志子系统

- 单条日志、进程内句柄缓存：目标变更时才重开；`stdout`/`stderr` 特殊值不缓存；常规路径 `fopen(…, "a")` + 每条 `flock(LOCK_EX) → fwrite → fflush → flock(UN)`，fpm 多进程并发安全。
- `/proc/1/fd/1`：按普通文件 open append，容器内（root）等价写 pid1 的 stdout，被 `docker logs` 收集；打开失败降级 stderr 并**每进程只告警一次**（`mre.log_file` 为空同样告警一次并走 stderr），不会反复刷屏或崩溃。
- 父目录自动创建（`mkdir -p` 语义）。
- 写路径不分配 Zend 内存、只用栈缓冲——保证在 mysqlnd/streams 钩子内、甚至 shutdown 期间调用都安全。
- JSON 输出手工转义（引号/控制字符），UTF-8 原样透传。

## 6. 阶段B：日志路由总框架

`mre_log_write()` 在写每条记录前调用 `mre_route_resolve()`（mre_rules.c）：

```
记录(type,dir,content,extra)
        │
        ├─ 1) mre.log_script 脚本回调 ── return '路径' ──► 用它
        │         └ 失败/null/异常 → 继续
        ├─ 2) yaml 规则（首中生效）──► 用该规则的 log_file
        │         └ 都不中 → yaml default_log_file（有 yaml 时）
        └─ 3) mre.log_file 主日志
```

路由只改目标路径；记录格式、flock、句柄缓存全部复用 §5 的写入器。
另有 `mre_log_write_main()`（绕过路由直写主日志），专用于脚本失败的一次性告警，
避免 告警→路由→脚本→再告警 的递归。

## 7. yaml 规则引擎（mre_rules.c）

- 规则来自 yaml 顶层 `rules:` 列表（`name/type/match/log_file`，`log` 为 `log_file`
  的别名）与 `default_log_file`；仅当 `match` 与 `log_file` 齐全才生效，残缺规则
  stderr 告警并跳过。
- **PCRE2 接入方式（关键取舍）**：扩展不链接 libpcre2，而是自带 6 个 pcre2 函数的
  extern 声明（`pcre2_compile_8 / pcre2_match_8 / pcre2_match_data_create_from_pattern_8 /
  pcre2_match_data_free_8 / pcre2_code_free_8 / pcre2_get_error_message_8`），让动态
  链接器解析到 PHP 进程自身的 PCRE2——Debian/Ubuntu 的 PHP 本身动态链接
  `libpcre2-8.so.0`（全局作用域可见），源码编译的 PHP 二进制以 `-export-dynamic`
  导出全部全局符号。所用选项值（CASELESS 0x8 / DOTALL 0x20 / EXTENDED 0x80 /
  MULTILINE 0x400 / UNGREEDY 0x40000 / UTF 0x80000 / ANCHORED 0x80000000）为
  PCRE2 10.x 稳定 ABI 常量。这样零新增构建依赖、与 PHP 共用同一份 PCRE2、
  且编译失败只产生我们自己的清晰告警（不会被 PHP 的 E_WARNING 打到用户输出）。
- pattern 支持 preg 风格 `"定界符/修饰符"`（`i m s x u U A`），定界符对
  `()[]{}<>` 特殊处理；无定界符时整串按 pattern 使用；编译失败跳过该规则并
  stderr 告警（含规则名与 pcre2_get_error_message 文本）。
- **缓存**：规则数组（含 pcre2_code 与复用的 match_data）存活于进程级 malloc 内存；
  以 `(yaml_root 指针, yaml mtime)` 判断是否需要重建——只在 yaml 加载/热加载时重编译，
  匹配路径零编译开销。MSHUTDOWN 统一释放。
- 匹配：按规则顺序 `pcre2_match`，`type` 过滤（空=都匹配）；首中即用其 `log_file`，
  全不中用 `default_log_file`（仅当 yaml 已加载），否则返回 0 交回主日志。
- `mre_yaml_dump()` 追加输出 `rules_compiled`（生效规则 + compiled 状态）与
  `default_log_file`；未配置 yaml 时保持阶段A行为返回 `null`。

## 8. 脚本回调日志路径（mre_script.c）

- 执行模型（BUG-2 根治方案，替换早期"zend_compile_file 编译 + zend_execute 直调 +
  (mtime,size) 每请求缓存"方案）：脚本经一段**固定的 PHP 层包装串**执行——

  ```php
  try { $___mre_ret = include $___mre_path; }
  catch (Throwable $___mre_e) { $___mre_ret = null; $___mre_warn = $___mre_e->getMessage(); }
  ```

  由 `zend_eval_stringl()` 编译并执行。**异常从不越过 op_array 边界进入 C 层**：
  运行时异常与 include 解析错误（`ParseError`，7.0 起即可被 catch 的 `Throwable`）
  都被包装串的用户态 catch 吃掉。旧方案把脚本 op_array 直接交给 `zend_execute`，
  未捕获异常从顶层码帧逃逸后的引擎 unwind 路径在 7.4 上有 GPF（容器实测 BUG-2，
  2963935 的"逃逸栈顶帧状态下 clear_exception"修复实测无效）；新方案使这条危险
  路径不可达，是唯一被容器实测证明可靠的修法方向。
- **C 层不再做任何引擎异常状态手术**：没有 `zend_clear_exception()`、没有
  `getMessage()` 探测（旧 `mre_exception_summary` 整个删除）、没有对
  `EG(opline_before_exception)` 的顾虑。仅剩两处引擎状态操作，均为引擎自身语义：
  - `EG(current_execute_data)=NULL`：`zend_execute`（`zend_eval_stringl` 内部使用）
    此时压入挂在 `&EG(symbol_table)` 上的 `ZEND_CALL_TOP_CODE` 帧，包装串与被
    include 的脚本都跑在全局符号表上，`$context`/`$___mre_*` 对脚本如同 {main} 的
    全局变量，且绝不触碰被打断代码的局部作用域；执行后恢复调用方帧。
  - `EG(exception)` 指针保存/恢复（挂起异常摘除与归还）：挂起异常对包装串不可见
    （否则引擎会跳过执行或把它路由进 catch），返回后归还给属主。纯指针换手，
    不调用任何清理函数。
- **包装串与路径注入**：包装串是常量字符串，只引用 `$___mre_path/$___mre_ret/
  $___mre_warn` 变量，脚本路径经全局符号表注入——路径永不内插进包装串（杜绝引号
  注入破坏包装结构）。结果同样从全局符号表读回：`$___mre_warn` 为字符串则发一次
  `type:"warn"` 主日志告警（每进程一次），`$___mre_ret` 为非空字符串且短于缓冲区
  则作为本条记录的目标路径；随后删除注入的四个全局变量（`context` 与三个 `___mre_*`）。
- **编译缓存取舍（简化）**：不再缓存任何 op_array。包装串约 140 字节，每条记录
  编译执行一次（8.2 实测 ~2µs/条）；脚本本身的编译由 `include` 走引擎标准路径，
  启用 opcache 时命中共享内存缓存（fpm 常态，等效于旧缓存效果），未启用 opcache
  时每条记录重新读盘编译。换来的好处：引擎代管 op_array 生命周期，"opcache 共享
  内存 op_array 不可销毁"这一类风险整体消失；旧 `script_oparray/mtime/size` 全局
  字段与 7.4/8.x 两套 `zend_file_handle`/`zend_compile_file` 分支一并删除。
- **失败降级**：`$___mre_ret` 非字符串/空（含 `return null`、`return 42`、无 return
  的 `1`）→ 静默降级不告警；包装串 catch 到异常 → `$___mre_warn` 携带消息摘要 →
  每进程一条 `type:"warn"`；`stat()` 失败（脚本不存在）→ 一次性 "stat() failed"
  告警（保留旧语义，避免每条记录的 include E_WARNING 噪音）。
- **echo 捕获**：执行前后经 function_table 查找调用 `ob_start`/`ob_end_clean`
  （缺失则跳过），脚本输出被捕获丢弃，不混入业务输出流。
- **exit()/die()**：7.4 是真 bailout（`zend_catch` 捕获：恢复帧/异常、摘除注入
  变量、重新 bailout，按引擎预期结束请求）；8.0 起 exit 改为
  `zend_throw_unwind_exit()` 优雅 unwind 标记，会浮出到包装串调用的 C 边界——
  检测到该标记（`zend_is_unwind_exit/zend_is_graceful_exit`，仅 8.x 存在）时保持
  其挂起让引擎完成用户请求的退出（exit 状态码保留），本条记录静默降级，期间
  C 侧收尾的记录仍会落盘，请求在下一条用户态边界终止。
- **$context 构建**：`type/dir/content/extra/headers/post/cookie/get/session_id/uri/method`
  全字段（README 有表）。`headers` 由 `$_SERVER` 的 `HTTP_*` 与 `CONTENT_TYPE`/
  `CONTENT_LENGTH` 整理为小写连字符名；`session_id()` 通过查 function_table 后
  `zend_call_function` 调用（不依赖 ext/session 编译期）。
- 编译与执行整体包 `zend_try/zend_catch`：脚本内致命错误（bailout 类，7.4 的
  exit 也算）触发 bailout 时先恢复 `EG(current_execute_data)`、摘除注入的全局
  变量，不把半恢复的执行器状态留给请求关闭流程。
- 防重入：`script_busy` 标志，脚本内触发的 SQL/redis 记录不再回调脚本；
  RSHUTDOWN 后 `script_available=0`（executor 关闭后执行脚本不安全）。
- 已知边界：脚本内 `exit()/die()` 终止当前请求（见上，记录可能丢失一条）；
  脚本顶层静态变量**每条记录重置**（旧方案的每请求 op_array 缓存会让 static
  跨记录共享，新方案每条记录都是一次独立 include）；脚本不应使用 `___mre_`
  前缀的全局变量（扩展内部保留名）。

## 9. 跨 fpm 全局事务（mre_gtx.c）

### 9.1 注册表

`<state_dir>/mre-gtx.reg`（行式文本，自定格式，见下）+ `<state_dir>/mre-gtx.lock`
（flock 串行化“读-改-写”）：

```
version 1
state active|mark_rollback|mark_commit
gtx_id <32位hex>
started_at <unix>
timeout <sec>
owner_pid <pid>
conn <key> <pid> <registered-ts> <0|1 pending>
```

`conn key` = `主机:端口:server_thread_id:pid`（主机名做字符白名单清洗），
server thread id 由 MySQL 分配，跨进程唯一。

- **写**：先写 `<reg>.tmp.<pid>`，`fflush+fsync+rename` 原子替换。
- **锁**：所有“读-改-写”在 `mre-gtx.lock` 的 `flock(LOCK_EX)` 下进行，锁内只有
  文件 IO 与内存操作（微秒级），绝不发网络/SQL；`state=none` 时以 unlink 结束窗口。
- **读**（钩子快照路径）不需要锁：rename 原子性保证读到的必然是完整版本。

### 9.2 窗口语义（与 README 对应）

1. `mre_gtx_begin()`：RMW 创建窗口（幂等拒绝：存活窗口存在时返回 false；
   超时窗口与无存活成员的收尾窗口可被替代）。`mre.gtx=0` 时全部函数直接 false。
2. **登记**：mysqlnd `query/stmt_execute` 钩子 `post_call`：语句成功后若
   `SERVER_STATUS_IN_TRANS` 或 SQL 为 BEGIN/START TRANSACTION，且快照显示窗口
   active → RMW 把连接 key 加入 `conns`（仅 active 窗口接受登记）。
   覆盖显式 BEGIN 与 autocommit=0 后的首语句（后者由服务端事务状态位驱动）。
3. **延迟 COMMIT**：`pre_call` 在语句发出前检查：tracked 连接的 COMMIT 被吞掉
   （不触达 server），RMW 将该条目 `pending=1`，钩子记录请求/响应日志后直接返回
   PASS——业务拿到 `commit() === true` 而事务保持打开。
4. **统一收尾**：`mre_gtx_commit()/mre_gtx_rollback()` 只打标记（purge 死进程条目，
   无存活成员时窗口立即结束）；各持有连接的进程在其**下一次 mysqlnd 调用入口**
   （pre_call）发现 mark_rollback/mark_commit → 通过 `mre_orig_query` 直发真实
   `ROLLBACK`/`COMMIT`（绕过自身钩子避免递归；写入可见的 req/resp 日志）→
   RMW 注销自身；最后一条移除时窗口结束。业务主动 `ROLLBACK` 视为退出窗口。
5. **清理**：每次 RMW/状态读取顺带 `kill(pid,0)` 判活清理（EPERM 视为存活）；
   超时（`timeout` 字段，来自 begin 时的 `mre.gtx_timeout`）的 active 窗口在
   首次访问时被标记 `mark_rollback`（安全优先）——此后各连接入口统一回滚。
6. **连接关闭**：dtor 钩子里 tracked/pending 的连接直接注销（其事务由服务端
   断开语义回滚）；这是“连接在收尾前关闭”场景的兜底。

### 9.3 开销控制

- 快照缓存：进程内保存 (mtime,size,解析结果)；`stat` 变化才重读。
- mysqlnd 侧节流：每请求每连接最多一次 stat（`gtx_epoch` 在 RINIT 递增，
  连接上下文记录上次检查的 epoch）；BEGIN/COMMIT/ROLLBACK 类控制语句强制
  刷新一次（语句级低频，保证拦截判定新鲜）。
- `mre.gtx=0` 时钩子第一分支即返回，开销为一次布尔判断。

### 9.4 已知局限

- 收尾依赖“连接的下一次 mysqlnd 调用”：再无调用的连接推迟到连接关闭（服务端
  回滚）或窗口超时。
- 未读结果集（unbuffered）状态下直发 ROLLBACK/COMMIT 会 commands-out-of-sync；
  该次收尾失败仍注销连接，由服务端断开回滚兜底。
- 拦截为连接级：窗口期间该连接的所有 COMMIT 都被延迟。
- 业务长事务 + 窗口超时 → 超时标记全局回滚（安全优先，业务需自行保证窗口期）。
- Windows 无 kill() 判活（仅超时清理）；本扩展以 Linux 部署为主。

## 10. 旧规划存档

阶段A设计文档曾在 §6 规划过本阶段三项功能（yaml 规则引擎、脚本回调日志路径、
跨 fpm 全局事务），并预留了 `mre.state_dir`、树访问器、`mre_yaml_dump()` 等
接入点。规划均已按 §6-§9 落地，落地版本与原规划的差异：

- 正则统一 PCRE2（7.4/8.x 同源），未走 pcre_exec 旧 API；
- 规则路径键以 `log_file` 为主、`log` 为兼容别名（原规划为 `log`）；
- 脚本回调初版曾采用"每请求编译缓存 + zend_execute 隔离帧"（含一次 7.4 异常
  清理时序修复，容器实测无效），**现改为 php 层 try/catch include 包装串执行**
  （见 §8），并补 ParseError/非字符串降级/exit 传播的回归断言；
  未做软超时（php 侧无法安全打断 C 栈，已在局限中说明 exit 语义）；
- 函数名定为 `mre_gtx_begin/commit/rollback/status`（原规划的 `mre_gtxn_*` 改名）；
- 注册表为行式文本 + 独立锁文件（原规划为单 json 文件），行为语义一致。
